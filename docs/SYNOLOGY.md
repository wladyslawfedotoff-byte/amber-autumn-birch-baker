# Развёртывание «Пора — время делать» на Synology (Container Manager)

GitHub — источник правды. На NAS работает один контейнер с Node-сервером; снаружи — только HTTPS через Reverse Proxy DSM:

```
https://pora.example.synology.me:8443  →  http://127.0.0.1:8080 (контейнер pora-app)
```

## Что где хранится

- **Данные на сервере (с 1.12.0 — база SQLite).** Задачи, списки, привычки, вехи, проекты, карточки «Обслуживания», рабочие часы, пароли, сменённые в приложении, подписки на пуши, список вложений и беседы помощника хранятся в одном файле **`/data/pora.db`** внутри контейнера (= `./data/pora.db` в папке проекта на NAS; рядом служебные `pora.db-wal` и `pora.db-shm` — их не трогайте и не копируйте по отдельности). До 1.12.0 это были JSON-файлы `pora.json`, `users.json`, `push.json`, `attachments/meta.json`, `assistant/…`; при первом старте 1.12 они переносятся в базу автоматически и откладываются в `./data/legacy-json-<дата>/` (п. 6.1). Каждое устройство держит локальную копию (офлайн работает) и синхронизируется с сервером через `GET/PUT /api/sync` (ревизии, ETag/If-Match, слияние по записям — телефон и компьютер не затирают друг друга).
- **Ежедневная копия базы:** `./data/backup/pora-<дата>.db` — целостный снимок (`VACUUM INTO`) каждую ночь после 03:00, хранятся 7 последних (`DB_SNAPSHOT_HOUR`, `DB_SNAPSHOT_KEEP`). Именно эти файлы надёжно восстанавливаются из Hyper Backup (п. 8.2).
- **Резервные копии** сервера: `./data/backups/pora-*.json` — не чаще раза в 30 минут; хранится самая свежая копия каждого из последних 24 часов и каждого из последних 30 дней (`BACKUP_INTERVAL_MINUTES`, `BACKUP_HOURLY`, `BACKUP_DAILY`). Список и восстановление — [п. 8](#8-резервные-копии-и-восстановление). Ручная копия — в приложении: Настройки → «Резервная копия».
- **Профили и пароли:** логины и пароли — в `.env` (`APP_USERS`, `USER_<ЛОГИН>_PASSWORD_HASH`, п. 9). Пароль, сменённый в приложении, — scrypt-хэш в базе `./data/pora.db` (таблица `users`, файл 0600); он важнее `.env`. У каждого профиля свои задачи, общие задачи хранятся один раз.
- **Вложения (фото, PDF, сканы, документы, таблицы):** файлы — `./data/attachments/files/<id>`, список (кому принадлежит, к какой задаче/проекту) — в базе `./data/pora.db` (до 1.12 — `./data/attachments/meta.json`). Сами файлы в базу не кладутся. Отдаются только по `/api/attachments/<id>` вошедшему профилю, который видит задачу или проект; публичных ссылок нет. Предел — `ATTACH_MAX_MB` (п. 12). Папку `data/attachments` включите в Hyper Backup вместе с остальной `data/`.
- **Напоминания на телефоне:** подписки устройств и отметки «уже отправлено» — в базе `./data/pora.db` (до 1.12 — `./data/push.json`). Ключи — только в `.env` (п. 11).
- **Копия на устройстве:** телефон и компьютер держат свою копию в IndexedDB браузера, отдельно для каждого профиля; «Выйти» её стирает. Изменения без сети ждут в очереди на устройстве и уходят на сервер, когда связь вернётся.
- **Секрет сессий:** `./data/.session-secret` (создаётся автоматически, права 0600), если не задан `SESSION_SECRET`; `./data/.session-epoch` — счётчик для «Выйти на всех устройствах» (0600).
- Старая синхронизация через WebDAV / «Файл» **отключена**: сохранённый пароль WebDAV стирается из браузера при первом запуске новой версии, в настройках показывается короткая заметка.
- Postgres **не нужен**. Старый вход через Grok (`better-auth`, `VITE_AUTH_ENABLED=false`) не используется.

## Образ публичный, но без секретов

`ghcr.io/wladyslawfedotoff-byte/amber-autumn-birch-baker:latest` — **публичный** пакет: `docker login` и токен для pull не нужны. В образе нет паролей и ключей. Все секреты лежат **только** в файле `.env` на NAS рядом с `compose.yaml`; compose подключает его через `env_file`. Никогда не добавляйте секреты в `Dockerfile`, в `docker-compose*.yml` / `compose.yaml` или в ARG сборки.

CI (`.github/workflows/docker-ghcr.yml`) собирает и публикует образ при каждом push в `main` (теги `:latest` и `:sha-<short>`); для pull request только собирает и прогоняет smoke-тест контейнера.

## 1. Папка проекта

Итоговая структура на NAS:

```
/volume1/docker/pora/
├── compose.yaml   ← описание контейнера (без секретов)
├── .env           ← секреты: APP_PASSWORD или APP_PASSWORD_HASH, по желанию SESSION_SECRET и ключи помощника AI_*
└── data/          ← данные приложения: pora.db (+ -wal, -shm), backup/ (копии базы), backups/, attachments/, .session-secret, .session-epoch
```

Всё нужное для восстановления NAS «с нуля» — эта одна папка (`compose.yaml`, `.env`, `data/`): её и включайте в Hyper Backup (п. 8).

1. Package Center → установите **Container Manager** и **Text Editor** («Текстовый редактор», нужен для создания `.env`).
2. File Station → общая папка `docker` → создайте `pora`, внутри — **`data`**:
   `/volume1/docker/pora/data`
   (или по SSH: `mkdir -p /volume1/docker/pora/data`).
3. Права на `data`: контейнер сам выставляет владельца при старте (он стартует как root, готовит `/data` и затем работает от непривилегированного пользователя `node`, uid 1000). У root в контейнере только права `CHOWN`, `DAC_OVERRIDE`, `SETUID`, `SETGID` (`cap_drop: ALL` + `no-new-privileges` в compose) — этого хватает и с `PUID`/`PGID`. Если в журнале контейнера видно `папка данных … недоступна для записи`, сделайте одно из двух:
   - File Station → `docker/pora/data` → Свойства → Разрешения → дайте «Чтение и запись» (например, группе Everyone, с применением к вложенным);
   - или добавьте в `.env` строки `PUID=…` и `PGID=…` владельца папки (узнать: SSH → `id <ваш-пользователь-DSM>`, обычно `1026` и `100`).

Клонировать репозиторий на NAS **не обязательно** — для варианта A хватает `compose.yaml` и `.env`. Если клонируете, не вставляйте токен в URL (`https://<TOKEN>@github.com/…` остаётся в `.git/config` и истории shell). Используйте SSH-ключ (`git clone git@github.com:wladyslawfedotoff-byte/amber-autumn-birch-baker.git pora`) или credential helper.

## 2. Файл `.env` с секретами

Шаблон с подробными комментариями — [`.env.example`](../.env.example). Минимальный `.env`:

```dotenv
APP_PASSWORD='четыре-пять-случайных-слов-через-дефис'
```

(это пример формата — придумайте свою фразу).

или, лучше, хэш вместо открытого пароля:

```dotenv
APP_PASSWORD_HASH=scrypt:32768:8:1:<соль>:<хэш>
```

### Как создать `.env` на Synology

1. Откройте **Text Editor** (главное меню DSM) → «Файл» → «Создать».
2. Вставьте содержимое `.env.example` (или только нужные строки) и впишите свои значения.
3. «Файл» → «Сохранить как» → папка `docker/pora`, имя файла ровно **`.env`** (с точкой в начале, без `.txt`). Кодировка UTF-8.
4. Проверьте по SSH: `ls -la /volume1/docker/pora` — должны быть `compose.yaml`, `.env`, `data`.

Можно и подготовить файл на компьютере и загрузить через File Station — главное, чтобы имя было `.env`, а не `env.txt` / `.env.txt`.

**Файл обязателен:** если `.env` нет, проект не запустится (Compose: `Failed to load …/.env` или `env file …/.env not found`). Необязательный `env_file` (`required: false`) в Compose из Container Manager (v2.20) не поддерживается, поэтому используется обычный `env_file: - .env`.

### Права на `.env`

Читать файл должен только администратор:

- File Station → `docker/pora/.env` → Свойства → **Разрешения**: оставьте доступ только своей учётной записи администратора (или группе `administrators`), удалите `Everyone`, `users` и прочих пользователей. Если права наследуются от папки `docker`, отключите наследование для этого файла.
- По SSH дополнительно: `sudo chmod 600 /volume1/docker/pora/.env`. Container Manager работает от root и прочитает файл в любом случае.
- Не открывайте общий доступ (ссылки File Station) к папке `docker/pora`.

`.env` **никогда не попадает в GitHub**: он в `.gitignore` и `.dockerignore`, в репозитории лежит только шаблон `.env.example` без настоящих значений.

### Пароль и хэш

Нужна одна из переменных — **`APP_PASSWORD`** или **`APP_PASSWORD_HASH`** (scrypt, имеет приоритет). Рекомендуется **фраза из 4–5 случайных слов, 16+ символов**. Минимум — 12 символов: более короткий пароль не принимается (fail closed), при 12–15 символах вход работает, но в журнале при старте есть предупреждение `auth.weak_password`. **Внимание при обновлении:** раньше минимум был 8 — если ваш пароль короче 12 символов, после обновления будет страница «Вход не настроен»; замените пароль в `.env` (или задайте хэш) и пересоздайте контейнер. Пока ни одна не задана (или осталась заглушка `СМЕНИТЕ_МЕНЯ`), приложение ничего не показывает, кроме страницы «Вход не настроен» (fail closed), а `/api/health` работает.

Хэш рекомендуется: тогда открытого пароля нет ни в `.env`, ни в настройках контейнера (переменные окружения видны в Container Manager → Контейнер → Подробности и в `docker inspect` любому администратору DSM). Получить хэш (скрипт `scripts/hash-password.mjs` спросит пароль дважды, ввод скрыт):

```bash
# на NAS по SSH, без клона репозитория
sudo docker run --rm -it --entrypoint node ghcr.io/wladyslawfedotoff-byte/amber-autumn-birch-baker:latest scripts/hash-password.mjs
# или в уже запущенном контейнере
sudo docker exec -it pora-app node scripts/hash-password.mjs
# или на компьютере с Node 22 в клоне репозитория
node scripts/hash-password.mjs
```

Хэш выглядит как `scrypt:32768:8:1:<соль>:<хэш>` и содержит только `A–Z a–z 0–9 : _ -` — его можно вставлять в `.env` как есть, без кавычек.

### Символ `$` и кавычки в `.env`

Проверено на Docker Compose v2.20.1 (Container Manager DSM 7.2) и v5.6:

| Строка в `.env` | Значение в контейнере |
| --- | --- |
| `APP_PASSWORD=ab$cd` | `ab` — `$cd` считается подстановкой переменной (в журнале предупреждение) |
| `APP_PASSWORD="ab$cd"` | `ab` — в двойных кавычках подстановка тоже работает |
| `APP_PASSWORD='ab$cd'` | `ab$cd` — одинарные кавычки: всё буквально |
| `APP_PASSWORD=ab$$cd` | `ab$cd` — `$$` означает один `$` |
| `APP_PASSWORD=ab\$cd` | `ab\` — обратная косая черта **не** экранирует `$` |
| `APP_PASSWORD=ab #cd` | `ab` — « #» без кавычек начинает комментарий |

То есть в `env_file` (как и в самом compose-файле) `$` **без кавычек нужно удваивать** или брать значение в одинарные кавычки. Одинарную кавычку внутри `'…'` в Compose v2.20 записать нельзя. Пробелы внутри значения сохраняются. Проще всего — фраза из слов через дефис или пробел, без `$ ' " \ #`, или `APP_PASSWORD_HASH`.

**Сессии.** Cookie `__Host-pora_session` (по HTTPS; HttpOnly, Secure, SameSite=Lax). Сессия истекает через 30 дней без использования (продлевается раз в сутки при работе) и в любом случае через **90 дней** после ввода пароля — тогда нужно войти заново. **Выйти на всех устройствах:** Настройки → «Подключение» → «Выйти на всех устройствах» (с подтверждением) — завершает все сеансы, включая текущий; данные не удаляются. Смена пароля профиля (в `.env` или в приложении) разлогинивает устройства этого профиля, смена `SESSION_SECRET` — все. С профилями «Выйти на всех устройствах» касается только своего профиля. После обновления на эту версию каждое устройство один раз попросит войти (новый формат cookie, теперь с логином).

**Защита от подбора.** 5 неверных попыток за 15 минут с одного IP → 429 на 15 минут. Кроме того, после **50 неверных попыток со всех адресов** за 15 минут вход **новых** устройств закрывается на 15 минут (против перебора с многих IP); уже вошедшие устройства продолжают работать и синхронизироваться, их cookie это не затрагивает. Сбросить досрочно — перезапустить контейнер. Неудачные попытки пишутся в журнал: `login.failed ip=… ipSource=…`. Проверьте один раз после настройки прокси: введите неверный пароль с телефона по мобильной сети — в журнале должен быть внешний IP телефона и `ipSource=x-real-ip` (или `x-forwarded-for`). Если там `127.0.0.1`/`172.x` и `ipSource=socket`, прокси не передаёт адрес клиента, и лимит по IP фактически общий (см. п. 4).

## 3. Проект в Container Manager (вариант A, рекомендуется — готовый образ)

Сначала создайте `data/` и `.env` (п. 1–2). Затем Container Manager → **Проект** → **Создать**:

- Название: `pora`
- Путь: `/volume1/docker/pora`
- Источник: «Создать docker-compose.yml» и вставить содержимое [`docker-compose.ghcr.yml`](../docker-compose.ghcr.yml) (Container Manager сохранит его как `compose.yaml`). Основная часть:

```yaml
services:
  app:
    image: ghcr.io/wladyslawfedotoff-byte/amber-autumn-birch-baker:latest
    container_name: pora-app
    restart: unless-stopped
    init: true
    security_opt:
      - "no-new-privileges:true"
    cap_drop:
      - ALL
    cap_add:
      - CHOWN
      - DAC_OVERRIDE
      - SETUID
      - SETGID
    env_file:
      - .env
    environment:
      HOST: "0.0.0.0"
      PORT: "8080"
      NITRO_HOST: "0.0.0.0"
      NITRO_PORT: "8080"
      APP_URL: "https://pora.example.synology.me:8443"
      DATA_DIR: /data
      VITE_GROK_EXTENSIONS: "0"
    volumes:
      - ./data:/data
    ports:
      - "127.0.0.1:8080:8080"
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:8080/api/health').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"]
      interval: 30s
      timeout: 5s
      start_period: 20s
      retries: 3
```

→ «Далее» → «Готово». В `compose.yaml` секретов нет; **не** добавляйте `APP_PASSWORD` и другие секреты в `environment:` — значения из `environment` перекрывают `.env`, даже пустые.

`APP_URL` — публичный адрес **с портом** `:8443`: по нему сервер проверяет Origin у входа и изменений (защита от CSRF). Если заходите и по другому адресу, имя хоста всё равно должно совпадать с тем, что передаёт Reverse Proxy.

После изменения `.env` контейнер нужно **пересоздать**: простой «Перезапуск» оставляет старые значения. В Container Manager: Проект `pora` → «Собрать» (Build), либо по SSH:

```bash
cd /volume1/docker/pora && sudo docker compose up -d --force-recreate
```

### Вариант B: сборка на NAS

```bash
cd /volume1/docker/pora   # клон репозитория
cp .env.example .env      # задайте APP_PASSWORD или APP_PASSWORD_HASH

```

## 4. Reverse Proxy + HTTPS (порт 8443)

1. Панель управления → Портал входа → Дополнительно → **Обратный прокси** → Создать:
   - **Источник:** HTTPS, имя хоста `pora.example.synology.me`, порт **`8443`**. Галочку HSTS можно не ставить: приложение само отправляет `Strict-Transport-Security: max-age=31536000` на HTTPS-запросы (без `includeSubDomains` и `preload`, чтобы не затронуть другие сервисы на этом домене);
   - **Назначение:** HTTP, `localhost`, порт **`8080`**.
2. Заголовки клиента: DSM передаёт `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`. Приложение берёт IP клиента из `X-Real-IP` (если это корректный IP), иначе из последнего элемента `X-Forwarded-For`; по `X-Forwarded-Proto: https` выставляются `Secure`/`__Host-` у cookie и HSTS. Если проверка из п. 2 показывает `ipSource=socket`, добавьте в правиле прокси → «Пользовательский заголовок» → «Создать» → `X-Real-IP` = `$remote_addr`. Порт контейнера слушает только `127.0.0.1`, поэтому эти заголовки может прислать только прокси DSM.
3. **Сертификат:** Панель управления → Безопасность → Сертификат → «Добавить» → «Добавить новый сертификат» → «Получить сертификат от Let's Encrypt»: домен `pora.example.synology.me` (для DDNS `*.synology.me` можно выпустить wildcard `*.example.synology.me` — DSM сделает это без открытого порта 80). Затем «Настройки» (Settings) в том же разделе → для службы обратного прокси `pora.example.synology.me:8443` выберите этот сертификат. Продление автоматическое; если выпускали не wildcard, для продления должен быть доступен порт 80.
4. На роутере пробросьте внешний `8443` → NAS `8443`. Порт `8080` наружу **не** открывайте (compose слушает только `127.0.0.1`).

Проверка с NAS по SSH:

```bash
curl -s http://127.0.0.1:8080/api/health
# {"ok":true,"uptime":12,"dataWritable":true}
```

## 5. Здоровье, журнал, самовосстановление

- `GET /api/health` (без входа): `200 {"ok":true,…}` или `503`, если папка данных недоступна для записи или последняя запись не удалась. Проверка ничего не пишет на диск и кэшируется на 60 с.
- Healthcheck в образе и в compose раз в 30 с опрашивает `/api/health`; Container Manager показывает статус «healthy / unhealthy».
- При фатальной ошибке процесс завершается (`exit 1`), а `restart: unless-stopped` поднимает контейнер заново.
- **Журнал:** Container Manager → Контейнер → `pora-app` → **Журнал** или по SSH `sudo docker logs -f pora-app`. Одна строка на событие: `server.start`, `auth.ready`, `auth.weak_password`, `login.failed ip=… ipSource=…`, `login.rate_limited`, `csrf.blocked`, `auth.logout_all`, `sync.saved`, `sync.conflict`, `sync.write_failed`, `backup.failed`, `data.temp_removed`, `data.reloaded`, `http.5xx`, `data.not_writable`, `data.corrupt`, `process.uncaughtException`; с 1.12.0 — `storage.ready`, `storage.import_ok`, `storage.import_user`, `storage.legacy_moved`, `storage.import_failed`, `storage.fatal`, `db.snapshot` (п. 6.1). Повторяющиеся `login.rate_limited` и `csrf.blocked` пишутся не чаще раза в минуту (следующая строка содержит `suppressed=N`).
- **Драйвер журнала не задаётся.** Docker в Container Manager по умолчанию пишет журнал через собственный драйвер Synology `db` (настройка `"log-driver": "db"` в `dockerd.json`), и вкладка «Журнал» показывает только такие журналы. Если в compose указать `logging:` с другим драйвером (например `json-file`), вкладка покажет «Журналы отсутствуют» (`docker logs` при этом работает). Поэтому блока `logging:` в compose нет. Проверить: `sudo docker inspect -f '{{.HostConfig.LogConfig.Type}}' pora-app` → `db`. Драйвер фиксируется при создании контейнера, после правки compose контейнер нужно **пересоздать**. Сообщения, которые повторяются при переборе паролей или чужих запросах, приложение само пишет не чаще раза в минуту. На других хостах (не Synology) можно добавить ротацию: `logging: { driver: json-file, options: { max-size: "10m", max-file: "3" } }`.
- **autoheal (необязательно):** Docker сам не перезапускает контейнер в состоянии «unhealthy» (только упавший). Для этого в compose есть закомментированный сервис `willfarrell/autoheal`. Ему нужен `/var/run/docker.sock` — это полный контроль над Docker на NAS, включайте осознанно: раскомментируйте сервис и `labels: autoheal: "true"` у `app`.

## 6. Обновление

Container Manager → Образ → `ghcr.io/…/amber-autumn-birch-baker` → **Обновить**, затем Проект `pora` → Остановить → Запустить. Или по SSH:

```bash
cd /volume1/docker/pora
sudo docker compose pull
sudo docker compose up -d
```

Данные в `./data` и секреты в `.env` сохраняются между обновлениями.

**Перед каждым обновлением** сделайте копию данных: `sudo cp -a /volume1/docker/pora/data /volume1/docker/pora/data-before-<версия>` (или File Station → `docker/pora/data` → «Копировать в…»). Копия при остановленном контейнере — самая надёжная.

Если вы меняли `compose.yaml` (например, взяли блоки `security_opt`, `cap_drop`/`cap_add` из актуального [`docker-compose.ghcr.yml`](../docker-compose.ghcr.yml) или удалили блок `logging:`, из-за которого вкладка «Журнал» была пустой), контейнер нужно пересоздать: Проект → «Остановить» → «Собрать»/«Запустить», или `sudo docker compose up -d --force-recreate`.

### 6.1. Обновление на 1.12.0: данные переезжают в базу SQLite

Самое важное обновление: хранилище на сервере меняется с JSON-файлов на базу `data/pora.db`. Перенос делается сам, один раз, при первом запуске; клиенты, синхронизация, офлайн-очередь и iPhone работают как раньше, на устройствах ничего делать не нужно. `.env` и `compose.yaml` менять не нужно.

**Шаги:**

1. Container Manager → Проект `pora` → **Остановить**.
2. **Сделайте копию папки данных** (обязательно): File Station → `docker/pora/data` → «Копировать в…» → `docker/pora/data-before-1.12`, или по SSH:
   ```bash
   sudo cp -a /volume1/docker/pora/data /volume1/docker/pora/data-before-1.12
   ```
3. Container Manager → Образ → `ghcr.io/…/amber-autumn-birch-baker` → **Обновить** (или в проекте «Действие» → **Собрать**: образ скачается заново и контейнер пересоздастся). По SSH: `cd /volume1/docker/pora && sudo docker compose pull && sudo docker compose up -d`.
4. Откройте **Журнал** контейнера (п. 5) и проверьте перенос.

**Что должно быть в журнале** (по порядку):

- `storage.import_ok file=/data/pora.db revision=… lists=… tasks=… habits=… … check=ok` — данные записаны в базу, прочитаны обратно и **совпали с исходными** (количество и контрольная сумма sha256 по каждому разделу — задачи, списки, привычки, вехи, проекты, карточки, пароли, подписки, вложения, беседы — и отдельно по каждому профилю);
- `storage.import_user user=… tasks=… …` — по строке на профиль: сколько записей у него перенесено;
- `storage.legacy_moved to=/data/legacy-json-<дата> files=pora.json,…` — старые файлы отложены в эту папку (ничего не удаляется);
- `storage.ready backend=sqlite file=/data/pora.db`.

При следующих запусках будет только `storage.ready backend=sqlite …` — повторного переноса нет. Проверьте в приложении, что задачи на месте (Настройки → «Подключение» → ревизия та же, что была). В `data/` теперь `pora.db`, `pora.db-wal`, `pora.db-shm`, папки `backup/`, `backups/`, `attachments/files/` и `legacy-json-<дата>/` (в ней `pora.json`, `users.json`, `push.json`, `attachments/meta.json`, `assistant/…` — как были).

**Если что-то пошло не так:**

- `storage.import_failed … action="откат импорта; работаю на JSON-файлах, как 1.11…"` — перенос не прошёл проверку или файл повреждён. База **не используется** (откат транзакции), приложение работает на старых JSON-файлах как 1.11, ничего не потеряно. При следующем запуске перенос попробуется снова. Пришлите строку журнала разработчику; если файл повреждён — восстановите его из `data-before-1.12` или `backups/`.
- `storage.fatal …` и контейнер перезапускается — база `pora.db` есть, но не открывается или повреждена. Приложение **намеренно не стартует**, чтобы не начать с пустой базы поверх данных. Восстановите базу из `backup/pora-<дата>.db` (п. 8.4) или откатитесь (п. 6.2).
- `storage.fatal … нет ни pora.db с данными, ни pora.json, но есть следы прежних данных …` — в `data/` нет ни базы, ни JSON-файлов, зато есть `legacy-json-…/`, `backup/pora-….db` или `backups/pora-….json` (например, `pora.db` удалили или подключили не ту папку). Сервер не стартует, чтобы устройства не увидели «пустой» сервер. Верните базу (п. 8.4) или JSON-файлы (п. 6.2). Если пустой старт действительно нужен — добавьте в `.env` строку `PORA_START_EMPTY=true` на один запуск и затем уберите её.
- Перезапуск или отключение питания посреди переноса безопасны: пока перенос не подтверждён, база считается неготовой и перенос повторяется с нуля; JSON-файлы откладываются только после успешной проверки, а если сбой случился между проверкой и переносом файлов — это доделается при следующем запуске.

### 6.2. Откат на 1.11 (образ `sha-b7b9107`)

> ⚠️ Версия 1.11 не умеет читать `pora.db`. Если просто вернуть старые JSON-файлы из `legacy-json-<дата>/`, **всё, что изменено после обновления на 1.12, пропадёт** (останется состояние на момент переноса). Чтобы сохранить новые правки, сначала выгрузите базу в JSON (вариант А).

**Вариант А — с сохранением правок, сделанных в 1.12 (рекомендуется).** Пока работает 1.12:

```bash

# → /data/export-json-<дата-время>/: pora.json, users.json, push.json, attachments/meta.json, assistant/…
```

Затем:

1. Остановите проект `pora`.
2. Уберите базу в сторону (не удаляйте): `cd /volume1/docker/pora/data && sudo mkdir -p db-1.12 && sudo mv pora.db pora.db-wal pora.db-shm db-1.12/ 2>/dev/null`.
3. Скопируйте выгрузку в `data/`: `sudo cp -a export-json-<дата-время>/. ./` (файлы встанут на свои места, `attachments/meta.json` — рядом с `attachments/files/`).
4. В `compose.yaml` замените `image: …:latest` на `image: ghcr.io/wladyslawfedotoff-byte/amber-autumn-birch-baker:sha-b7b9107`, затем «Собрать» (или `sudo docker compose up -d`).

**Вариант Б — вернуть данные на момент обновления** (если 1.12 не запускается): остановите проект, уберите `pora.db*` в сторону (шаг 2 выше), скопируйте содержимое `legacy-json-<дата>/` обратно в `data/` (`sudo cp -a legacy-json-<дата>/. ./`) или верните всю папку `data-before-1.12`, и запустите образ `sha-b7b9107` (шаг 4).

**Снова на 1.12 после отката:** верните `image: …:latest`. Если `pora.db` убрана в сторону, перенос из JSON выполнится заново, как в первый раз. Если `pora.db` осталась в `data/`, а рядом появились JSON-файлы от 1.11, сервер сначала сохранит копию базы `backup/pora-<дата>-before-reimport-<время>.db`, затем перенесёт **изменённые** JSON-файлы поверх базы (ревизия повышается, устройства догрузят данные) и отложит их в `legacy-json-<дата>-N/`; в журнале — `storage.reimported`.

### 6.3. Обновление на 1.13.0 (быстрое добавление)

`.env` менять не нужно. При первом запуске база получает схему v2 (таблица ключей устройств `quick_tokens`), данные не переносятся.

1. Проект `pora` → **Остановить** → копия `data` в `data-before-1.13` (как в 6.1, п. 2).
2. **Собрать** (образ скачается заново).
3. В журнале: `storage.migrated … schema=2` (только при первом запуске), затем `storage.ready backend=sqlite`; `storage.fatal` быть не должно.

Пока работает 1.13: `sudo docker exec pora-app node scripts/db-downgrade-1.12.mjs` (сначала делает снимок `backup/pora-<дата>.db`, затем убирает только таблицу ключей; задачи не трогаются), сразу остановите проект и запустите образ `sha-32500bf`. Ключи телефонов после этого не работают — после возврата на 1.13 создайте новые.

## 8. Резервные копии и восстановление

Четыре уровня, от простого к надёжному:

### 8.1. Встроенные копии приложения (`data/backups`)

Делаются автоматически (см. «Что где хранится»). Список — по SSH:

```bash
sudo docker exec pora-app node scripts/restore-backup.mjs --list
```

Восстановить (контейнер может работать, лучше когда никто не редактирует задачи):

```bash
# посмотреть, что изменится, ничего не меняя
sudo docker exec pora-app node scripts/restore-backup.mjs pora-2026-10-06T07-30-00-000Z-r42.json --dry-run
# восстановить
sudo docker exec pora-app node scripts/restore-backup.mjs pora-2026-10-06T07-30-00-000Z-r42.json
# восстановить и удалить всё, что появилось после этой копии
sudo docker exec pora-app node scripts/restore-backup.mjs pora-2026-10-06T07-30-00-000Z-r42.json --replace
```

С 1.12.0 скрипт пишет в базу `pora.db` (одной транзакцией) и принимает также копию базы: в `--list` видны и `backup/pora-<дата>.db`, их можно указать вместо JSON (`… restore-backup.mjs pora-2026-10-18.db --dry-run`). Скрипт сначала сохраняет текущее состояние в `backups/pora-…-pre-restore.json` (откат — восстановить этот файл), затем возвращает записи из копии с новой отметкой времени и повышает ревизию. Устройства получат восстановленные данные при следующей синхронизации (до ~15 с или «Синхронизировать сейчас»); **очищать данные сайта на устройствах не нужно** — восстановленные записи побеждают их локальные копии. Без `--replace` записи, созданные после копии, остаются; с `--replace` они удаляются на сервере и на всех устройствах. Можно указать и файл, выгруженный из приложения (Настройки → «Резервная копия»), предварительно положив его в `data/`: `… restore-backup.mjs /data/pora-backup.json`.

### 8.2. Hyper Backup (копия вне NAS-диска)

> **С 1.12.0 — важно про базу.** `pora.db` работает в режиме WAL: часть последних изменений лежит в `pora.db-wal`, и файл, скопированный «на ходу», может оказаться несогласованным. Поэтому сервер каждую ночь (после `DB_SNAPSHOT_HOUR`, по умолчанию 03:00 по `TZ` контейнера) делает **целостный снимок** `data/backup/pora-<дата>.db` командой `VACUUM INTO` и проверяет его (`PRAGMA quick_check`); хранятся 7 последних (`DB_SNAPSHOT_KEEP`). Ставьте задачу Hyper Backup **после** этого времени (например, на 04:00) — тогда в копии гарантированно есть согласованная база за прошедшую ночь. Снимок вручную, например перед рискованным шагом или внеплановым запуском Hyper Backup:
> ```bash
> sudo docker exec pora-app node scripts/db-snapshot.mjs
> ```
> Восстанавливать из Hyper Backup — файл из `data/backup/`, а не «живой» `pora.db` (п. 8.4). В журнале каждый снимок — строка `db.snapshot`.

Встроенные копии лежат на том же диске — от поломки диска или NAS они не спасут. Package Center → **Hyper Backup** → «Создать» → «Задача резервного копирования данных» → место назначения (USB-диск, другой NAS, Synology C2 или облако) → в списке папок отметьте **`docker/pora`** целиком: это `data/` (задачи, копии, ключ сессий) и `.env` (пароль или хэш). Дальше:

- расписание — ежедневно (ночью);
- ротация — «Включить ротацию резервных копий» → Smart Recycle (например, 30 версий);
- **включите шифрование на стороне клиента** — в копии лежит `.env` с паролем/хэшем; ключ шифрования сохраните отдельно;
- после первой копии проверьте восстановление: Hyper Backup → «Восстановить» → «Данные» → выбрать версию → восстановить `docker/pora` в другую папку и убедиться, что там есть `data/backup/pora-<дата>.db` (до 1.12 — `data/pora.json`) и `.env`.

Полное восстановление: остановите проект `pora` в Container Manager, восстановите папку `docker/pora` из Hyper Backup на место, затем замените базу свежим снимком из `data/backup/` (п. 8.4) и запустите проект. Устройства догрузят свои изменения, сделанные после копии (если нужно откатить и их — восстановите нужный файл через п. 8.1 с `--replace`).

### 8.3. Снимки Btrfs (по желанию)

Если том — Btrfs: Package Center → **Snapshot Replication** → «Снимки» → общая папка `docker` → «Снимок» → «Настройки» → расписание (например, каждый час) и «Сохранение» (например, 24 ежечасных и 30 ежедневных). Снимки делаются мгновенно и почти не занимают места, но лежат на тех же дисках — это защита от ошибок и шифровальщиков, а не замена Hyper Backup. Восстановить данные: включите «Сделать снимок видимым» и скопируйте из `#snapshot` файл `data/backup/pora-<дата>.db` (1.12+) или `pora.json` (до 1.12) в `data/backups/`, затем `restore-backup.mjs <имя>` (п. 8.1); откатить всю папку — Snapshot Replication → «Снимки» → `docker` → выбрать снимок → «Восстановить к этому снимку» (при остановленном проекте).

### 8.4. Восстановить базу целиком из `backup/pora-<дата>.db`

Если `pora.db` повреждена (в журнале `storage.fatal`) или нужно вернуть всё состояние на дату снимка:

```bash
cd /volume1/docker/pora
sudo docker compose stop                     # или «Остановить» в Container Manager
cd data
sudo mkdir -p db-broken && sudo mv pora.db pora.db-wal pora.db-shm db-broken/ 2>/dev/null
sudo cp -p backup/pora-2026-10-18.db pora.db  # нужная дата
cd .. && sudo docker compose start
```

Файлы `-wal` и `-shm` от старой базы **обязательно уберите** вместе с ней — к другой базе они не подходят. Устройства догрузят на сервер свои изменения, сделанные после снимка. Вернуть только задачи, не трогая пароли и подписки, можно мягче — через `restore-backup.mjs` с файлом `.db` (п. 8.1).

## 9. Профили: несколько пользователей

У каждого профиля свой логин, пароль и свои задачи. Задачей или списком можно поделиться («Совместная») или поручить её другому («Назначить») — она появится у него в «Сегодня», календаре и разделе «Общие». Права проверяет сервер: чужие личные задачи не приходят на устройство вовсе.

### 9.1. Переход с одного пароля на профили (данные сохраняются)

Сейчас в `.env` один `APP_PASSWORD` или `APP_PASSWORD_HASH`. Все задачи на сервере после перехода принадлежат **`APP_OWNER`** (по умолчанию — первый логин в `APP_USERS`). Файл данных при этом не переписывается: у задач без владельца владелец считается «по умолчанию».

1. Сделайте копию: `sudo cp -a /volume1/docker/pora/data /volume1/docker/pora/data-before-profiles` (или проверьте свежую копию в Hyper Backup).
2. Получите хэш пароля для второго профиля (спросит пароль дважды):
   ```bash
   sudo docker exec -it pora-app node scripts/hash-password.mjs user2
   # → USER_USER2_PASSWORD_HASH=scrypt:32768:8:1:…
   ```
3. Добавьте в `/volume1/docker/pora/.env` (старые строки `APP_PASSWORD` / `APP_PASSWORD_HASH` **оставьте** — это пароль владельца):
   ```dotenv
   APP_USERS=user1,user2
   APP_OWNER=user1
   USER_USER1_NAME=Пользователь 1
   USER_USER2_NAME=Пользователь 2
   USER_USER2_PASSWORD_HASH=scrypt:32768:8:1:<соль>:<хэш>
   ```
   Логины — латиница `a–z`, цифры, `_` и `-`. Имя переменной: `USER_` + логин заглавными (`-` → `_`).
4. Пересоздайте контейнер (переменные `.env` читаются только при создании): Container Manager → Проект `pora` → «Остановить» → «Собрать»/«Запустить», или `cd /volume1/docker/pora && sudo docker compose up -d --force-recreate`.
5. Проверьте журнал: `auth.ready mode=users users=user1,user2 owner=user1`. Если есть `auth.user_problem` — у профиля нет пароля или он короче 12 символов (такой профиль не может войти, остальные работают).
6. На каждом устройстве один раз войдите заново, теперь с полем «Логин». Владелец видит все прежние задачи; у второго профиля — пусто. Устройство, на котором раньше работал владелец, при входе другим профилем не переносит его данные: оно загружает только данные вошедшего.

Откат: уберите строки шага 3 и пересоздайте контейнер — всё снова видно под одним паролем (задачи второго профиля тоже окажутся в общем списке, ничего не удаляется).

### 9.2. Добавить ещё одного пользователя

Профилей может быть сколько угодно, например `APP_USERS=user1,user2,user3`; для каждого логина задаются свои строки `USER_<ЛОГИН>_NAME` и `USER_<ЛОГИН>_PASSWORD` (или `USER_<ЛОГИН>_PASSWORD_HASH`). Логин — любое слово из латиницы a–z, цифр, `_` и `-`.

Допишите логин в `APP_USERS` (`APP_USERS=user1,user2,user3`), добавьте `USER_USER3_PASSWORD_HASH=…` (п. 9.1, шаг 2) и по желанию `USER_USER3_NAME=Пользователь 3`, пересоздайте контейнер. Убрать пользователя: удалите его из `APP_USERS` — его задачи остаются в файле и вернутся, если добавить логин снова.

### 9.3. Сменить пароль

- **В приложении:** Настройки → «Профиль» → «Сменить пароль» (текущий пароль и новый дважды, минимум 12 символов). Новый пароль сохраняется хэшем в `data/users.json` и работает вместо пароля из `.env`; остальные устройства этого профиля выходят, другие профили не затрагиваются.
- **Через `.env`:** замените `USER_<ЛОГИН>_PASSWORD_HASH` и пересоздайте контейнер. Если пароль уже меняли в приложении, сначала сбросьте его (п. 9.4) — иначе действует пароль из приложения.

### 9.4. Забыли пароль — сброс

```bash
sudo docker exec pora-app node scripts/reset-password.mjs --list    # у кого пароль задан в приложении
sudo docker exec pora-app node scripts/reset-password.mjs user2     # снова действует пароль из .env
```

Скрипт удаляет пароль профиля из базы (`data/pora.db`; до 1.12 — `data/users.json`) и разлогинивает его устройства; перезапуск не нужен. Если забыт и пароль из `.env` — задайте новый хэш (п. 9.1, шаг 2), пересоздайте контейнер и выполните сброс.

### 9.5. Резервные копии профилей

Вместе с `backups/pora-….json` сохраняется `backups/users-….json` (пароли, сменённые в приложении). Восстановление задач — как обычно (п. 8.1, общие и личные задачи возвращаются каждому владельцу). Вернуть пароли из копии: остановите проект, `sudo cp -p data/backups/users-<время>.json data/users.json` и запустите — при старте 1.12 сервер сохранит копию базы и перенесёт этот файл в неё (`storage.reimported`), сам файл уйдёт в `legacy-json-…/`.

## 10. Помощник (необязательно)

«Помощник» — чат, который читает ваши задачи и предлагает план дня, шаги, новые задачи и привычки. Всё, что он предлагает изменить, приходит карточкой и применяется только после «Применить». Модели задаются в `.env` (подробно с примерами — в `.env.example`); после правки `.env` пересоздайте контейнер (Container Manager → Проект → **Остановить** → **Собрать**, или `sudo docker compose up -d`). Без строк `AI_*` пункта «Помощник» нет.

Модели спрашиваются по очереди (`AI_PROVIDERS`): домашний ПК, если включён, затем бесплатные облачные, последней — платная. При ошибке, лимите (429), тайм-ауте или исчерпанной квоте берётся следующая модель, а неудачная пропускается 5 минут. Состояние каждой (доступен / лимит / ошибка) видно в «Настройки → Помощник»; ключи там не показываются. Если не ответил никто, в чате есть «Повторить» и «Отложить»: сервер сам переспрашивает (через 5, 10, затем каждые 15 минут, не дольше суток), ответ появится в той же беседе и в колокольчике («Помощник ответил»).

### 10.1. Локальная модель на ПК с Windows

Данные не уходят из домашней сети. На ПК подойдёт Ollama (10.1.1) или LM Studio (10.1.2) — что удобнее; оба отдают OpenAI-совместимый API. Для видеокарты 8 ГБ рекомендуется Qwen2.5 7B Instruct (умеет вызывать функции; другие модели 7–8B instruct с поддержкой tool use тоже подойдут, без неё помощник перейдёт на ответ в JSON).

Тип сервера можно указать (`AI_LOCAL_TYPE=ollama` или `lmstudio`) или оставить `auto`: сервер «Поры» сам спросит ПК `/api/tags` (Ollama), затем `/v1/models` (LM Studio). Старые `AI_OLLAMA_URL` / `AI_OLLAMA_MODEL` продолжают работать.

#### 10.1.1. Ollama

1. Установите Ollama для Windows с официального сайта и скачайте модель (PowerShell): `ollama pull qwen2.5:7b-instruct`.
2. Разрешите доступ из сети: «Параметры → Система → О системе → Дополнительные параметры системы → Переменные среды» → новая переменная пользователя `OLLAMA_HOST` = `0.0.0.0`. Закройте Ollama в трее и запустите снова.
3. Брандмауэр — **только локальная сеть** (PowerShell от администратора):
   ```powershell
   New-NetFirewallRule -DisplayName "Ollama LAN" -Direction Inbound -Protocol TCP -LocalPort 11434 -RemoteAddress LocalSubnet -Profile Private -Action Allow
   ```
   Сеть Wi-Fi/Ethernet должна быть «Частной». Не пробрасывайте порт 11434 на роутере: у Ollama нет пароля.
4. Закрепите за ПК постоянный IP в роутере (резерв DHCP) и проверьте с NAS: `curl http://192.168.1.50:11434/api/tags` — должен вернуться список моделей.
5. В `.env` на NAS:
   ```
   AI_PROVIDERS=local
   AI_LOCAL_TYPE=ollama
   AI_LOCAL_URL=http://192.168.1.50:11434
   AI_LOCAL_MODEL=qwen2.5:7b-instruct
   ```

#### 10.1.2. LM Studio

1. Установите LM Studio для Windows с официального сайта. Во вкладке поиска моделей найдите **Qwen2.5 7B Instruct** (GGUF, квантование **Q4_K_M**, около 4,7 ГБ — помещается в 8 ГБ видеопамяти) и скачайте.
2. Откройте вкладку **Developer** (в старых версиях — значок `>_`), выберите модель вверху (**Select a model to load**) и загрузите её. Длину контекста поставьте не меньше 8192.
3. В **Settings** сервера на этой вкладке включите **Serve on Local Network** (иначе сервер слушает только сам ПК), порт оставьте `1234`. Включите сервер переключателем **Start server** (статус **Running**). Чтобы сервер поднимался сам, в настройках приложения включите запуск при входе в систему, а модель оставьте загруженной (или включите загрузку модели по запросу — Just-in-Time).
4. Брандмауэр — **только локальная сеть** (PowerShell от администратора):
   ```powershell
   New-NetFirewallRule -DisplayName "LM Studio LAN" -Direction Inbound -Protocol TCP -LocalPort 1234 -RemoteAddress LocalSubnet -Profile Private -Action Allow
   ```
   Сеть должна быть «Частной». Не пробрасывайте порт 1234 на роутере: ключ серверу не нужен, значит, и защиты нет. Если Windows сама спросит про доступ для LM Studio — разрешите только для частных сетей.
5. Закрепите за ПК постоянный IP и проверьте с NAS: `curl http://192.168.1.50:1234/v1/models` — в ответе будет `"id"` загруженной модели. Это и есть имя для `AI_LOCAL_MODEL` (или оставьте его пустым — возьмётся модель из этого списка).
6. В `.env` на NAS:
   ```
   AI_PROVIDERS=local
   AI_LOCAL_TYPE=lmstudio
   AI_LOCAL_URL=http://192.168.1.50:1234/v1
   AI_LOCAL_MODEL=qwen2.5-7b-instruct
   ```

Когда ПК выключен или спит, помощник отвечает «Помощник сейчас недоступен» (или берёт следующую модель цепочки). Доступность ПК проверяется запросом `/api/tags` (Ollama) или `/v1/models` (LM Studio) и запоминается на минуту.

### 10.2. Облачные модели: основная kie.ai, бесплатные OpenRouter — запасные

```
AI_PROVIDERS=kieai,openrouter

AI_KIEAI_BASE_URL=https://api.kie.ai/{model}/v1
AI_KIEAI_API_KEY=впишите-свой-ключ
AI_KIEAI_MODEL=gemini-3-8-flash-openai
AI_KIEAI_PAID=1
AI_KIEAI_MONTHLY_TOKENS=2000000
AI_KIEAI_CHECK_URL=https://api.kie.ai/api/v1/chat/credit
AI_KIEAI_JSON_FORMAT=0
AI_KIEAI_TOOLS=json
AI_KIEAI_REASONING_EFFORT=low

AI_OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
AI_OPENROUTER_API_KEY=впишите-свой-ключ
AI_OPENROUTER_MODEL=nvidia/nemotron-3-super-120b-a12b:free,google/gemma-4-31b-it:free,openrouter/free
AI_OPENROUTER_TOOLS=json
```

Порядок в `AI_PROVIDERS` — порядок опроса: сначала kie.ai; при ошибке, лимите (429/402), тайм-ауте или недоступности — бесплатные модели OpenRouter по списку (`openrouter/free` — их собственный выбор любой доступной бесплатной модели, последней). Ответ запасной модели подписан в чате «… · запасная модель». Домашний ПК, если он есть, можно поставить первым: `AI_PROVIDERS=local,kieai,openrouter`.

**OpenRouter: приватность.** Бесплатные модели OpenRouter работают у сторонних поставщиков, и часть из них может **сохранять запросы и использовать их для обучения** — а в запросе текст вопроса и нужные для ответа задачи. Поэтому OpenRouter здесь только запасной. В кабинете OpenRouter → Settings → Privacy выключите разрешение на обучение/логирование для бесплатных моделей, если оно есть; без этого часть моделей просто не ответит, и помощник возьмёт следующую. У бесплатных моделей есть дневной лимит запросов (без пополнения счёта — около 50 в день), а список меняется — сверяйте названия на openrouter.ai/models (фильтр «free»). `TOOLS=json` — модели отвечают в формате JSON, как kie.ai: так ответ предсказуемее, чем вызов функций у бесплатных моделей.

Имена (`openrouter`, `kieai`) — любые латиницей; по ним строятся переменные `AI_<ИМЯ>_…`. Список бесплатных моделей у сервисов меняется — проверьте актуальные названия. Многие бесплатные модели не умеют вызывать функции: помощник сам переходит на ответ в формате JSON. `AI_<ИМЯ>_PAID=1` помечает платный сервис; каждый пользователь может выключить «Разрешить платные» в «Настройки → Помощник». `MONTHLY_TOKENS` — потолок токенов в месяц: после него сервис пропускается до следующего месяца (счётчик — `data/assistant-usage.json`).

**kie.ai.** Оплата кредитами (пополнение в личном кабинете, при регистрации дают немного бесплатно), языковые модели списывают кредиты за миллион входных и выходных токенов — цена указана на странице каждой модели. Ключ — в разделе API Key кабинета, передаётся как `Authorization: Bearer`. OpenAI-совместимый чат (`/v1/chat/completions`, потоковый ответ, вызов функций) есть не у всех моделей и у каждой по своему адресу: `https://api.kie.ai/<модель>/v1/chat/completions`, поэтому в `BASE_URL` стоит `{model}`. Подходят модели с пометкой «OpenAI» в документации (например, `gemini-3-8-flash-openai`); другие модели kie.ai работают по иным протоколам и здесь не подойдут. Перед включением сверьте в документации kie.ai точное название модели и цену — список меняется. Несколько моделей можно перечислить через запятую. Ошибки kie.ai присылает с HTTP 200 и полем `code` (402 — кончились кредиты, 429 — лимит, 401 — неверный ключ): помощник понимает это и берёт следующую модель. «Проверить связь» запрашивает баланс по `CHECK_URL` — так видно, что ключ принят. `JSON_FORMAT=0` — ответ в JSON помощник попросит текстом, без отдельного параметра. `TOOLS=json` — обязательно для kie.ai: его чат-модели не выполняют чужие функции (у `gpt-5-2` в `tools` принимается только встроенный веб-поиск, остальное молча отбрасывается), и без этой строки модель отвечает «нет доступа к инструментам». В режиме JSON помощник сам описывает модели свои инструменты, а предложения по-прежнему приходят карточками с «Применить». Пример с GPT 5.2: `AI_KIEAI_BASE_URL=https://api.kie.ai/gpt-5-2/v1` (или `…/{model}/v1`) и `AI_KIEAI_MODEL=gpt-5-2`.

**`AI_<ИМЯ>_TOOLS`** (и `AI_LOCAL_TOOLS` для ПК): `auto` по умолчанию — сначала вызов функций; если сервис их отвергает или модель отвечает так, будто их нет, ответ тут же переспрашивается в режиме JSON, и до перезапуска контейнера эта модель сразу спрашивается в JSON (в журнале — `assistant.json_mode`). `json` — сразу JSON, `native` — только вызов функций. В режиме JSON модель может сначала попросить прочитать задачи — помощник выполнит чтение сам и переспросит (не больше 4 раз); служебный JSON на экран не попадает.

**Расход токенов.** Модель получает не все задачи, а только нужные для вопроса: на «что просрочено» — просроченные, на «спланируй день» — задачи дня и свободное время, на «добавь …» — свободное время на эту дату; описания инструментов — тоже только подходящие. Из беседы передаются последние 4 сообщения (длинные — обрезаны). Короткие правила стоят в начале запроса одинаковыми — сервисы с кэшем считают их дешевле. Ответ ограничен `AI_MAX_TOKENS` (по умолчанию 600; `AI_<ИМЯ>_MAX_TOKENS` — для одного сервиса, `0` — без ограничения). `AI_<ИМЯ>_REASONING_EFFORT=low` уменьшает «размышления» модели — для `gpt-5-2` на kie.ai это главная статья расхода. Простые вопросы («что просрочено?», «что на сегодня?», «свободные окна завтра») приложение считает само, без модели — в чате у ответа пометка «без модели»; выключается `AI_LOCAL_ANSWERS=0`.

### 10.3. Безопасность и данные

- Ключи только в `.env` на NAS (права 600, в Hyper Backup — вместе с папкой). В приложение, образ и репозиторий они не попадают.
- Облачная модель получает текст вопроса и только те задачи, что нужны для ответа, и только видимые этому пользователю (личные задачи других профилей — никогда). Перед первым ответом из облака показывается экран согласия, и ещё раз — когда облако впервые подменяет выключенный ПК. «Разрешить облако, когда ПК выключен» можно выключить в настройках.
- Беседы, очередь «Отложить» и уведомления хранятся на NAS в базе `data/pora.db` (до 1.12 — `data/assistant/<логин>.json`); беседу можно удалить в истории (☰ в чате).
- `AI_RATE_LIMIT` (по умолчанию 60 вопросов в час на пользователя) ограничивает расход.

## 11. Работа без сети и напоминания на телефоне

### 11.1. Без сети

Ничего настраивать не нужно. После первого входа «Пора» сохраняется на устройстве и открывается без интернета; правки без сети копятся («Нет сети · N ждут отправки» вверху) и отправляются сами, когда связь появится. Чтобы это работало на iPhone, откройте «Пору» хотя бы раз с сетью после обновления до 1.8.0.

### 11.2. Ключи уведомлений (один раз)

1. По SSH на NAS создайте пару ключей (контейнер уже обновлён до 1.8.0):
   ```
   sudo docker exec pora-app node scripts/push-keys.mjs
   ```
   Если контейнер не запущен — тем же образом без него:
   ```
   sudo docker run --rm --entrypoint node ghcr.io/wladyslawfedotoff-byte/amber-autumn-birch-baker:latest scripts/push-keys.mjs
   ```
   Можно и на любом компьютере с Node 22 в клоне репозитория: `node scripts/push-keys.mjs`.
2. Скрипт печатает две строки `PUSH_VAPID_PUBLIC_KEY=…` и `PUSH_VAPID_PRIVATE_KEY=…`. Добавьте их в `/volume1/docker/pora/.env` (File Station → открыть в текстовом редакторе) и третью строку со своим адресом:
   ```
   PUSH_VAPID_PUBLIC_KEY=<открытый ключ из вывода>
   PUSH_VAPID_PRIVATE_KEY=<закрытый ключ из вывода>
   PUSH_CONTACT=mailto:<ваш адрес>
   ```
   Кавычки не нужны: в ключах только `A–Z a–z 0–9 - _`. Закрытый ключ — секрет, как пароль: только в `.env`.
3. Container Manager → Проект `pora` → «Остановить» → «Собрать» (или «Запустить»): переменные из `.env` читаются при создании контейнера. В журнале появится `push.enabled timeZone=Europe/Moscow`. Если ключи с ошибкой — `push.disabled reason=keys_invalid`, а приложение работает без уведомлений.
4. Ключи создаются один раз. Новая пара выключит уведомления на всех устройствах, их придётся включить заново.

### 11.3. Включить на iPhone

1. Откройте «Пору» в браузере → «Поделиться» → «На экран „Домой“». На iPhone уведомления работают только так (iOS 16.4 и новее), во вкладке браузера — нет.
2. Откройте «Пору» с экрана «Домой» → «Настройки» → «Уведомления» → «Включить уведомления» → «Разрешить».
3. «Проверить» — через несколько секунд придёт тестовое уведомление.
4. В задаче: «Напомнить» → время и насколько заранее (в момент, за 5/15/30 минут, за час, за день). Напоминание приходит, даже когда приложение закрыто; нажатие открывает задачу. Каждый профиль включает уведомления на своём телефоне сам; «Выйти» отключает их на этом устройстве.

Время напоминаний — по часовому поясу устройства, которое включило уведомления (по умолчанию `Europe/Moscow`, можно сменить `APP_TIMEZONE` в `.env`). Если NAS был выключен, пропущенные напоминания приходят после запуска, но не старше 2 часов; одно и то же напоминание дважды не приходит.

## Troubleshooting

- **Уведомления не приходят на iPhone:** «Пора» должна быть открыта с экрана «Домой», а не во вкладке; в «Настройках» iPhone → «Уведомления» → «Пора» должны быть разрешены; режим «Фокус» может их прятать. Проверьте журнал: `push.enabled` при запуске, `push.sent` при отправке, `push.gone` — устройство отписалось (включите заново).

- **Помощник пишет «нет доступа к инструментам» или «не могу посмотреть задачи»:** у сервиса не работает вызов функций — добавьте `AI_<ИМЯ>_TOOLS=json` (для kie.ai — `AI_KIEAI_TOOLS=json`) и пересоздайте контейнер.
- **В журнале `assistant.stream_repaired`:** сервис прислал куски потока с «сырыми» управляющими символами — помощник их исправил, начало ответа не теряется. `assistant.stream_unparsed` — кусок разобрать не удалось; `assistant.json_unparsed` — модель вернула испорченный JSON, показан только текст ответа (предложения из него пропущены). Чтобы увидеть, что именно присылает сервис, временно добавьте `AI_DEBUG_STREAM=1` (журнал `assistant.stream_debug`, без ключей) и пересоздайте контейнер.
- **Ответ с пометкой «без модели»:** простой вопрос посчитан приложением по вашим задачам, токены не тратятся. Чтобы всегда спрашивать модель — `AI_LOCAL_ANSWERS=0`.
- **«Помощник сейчас недоступен»:** ПК выключен, сервер на нём не запущен или не пускает по сети (п. 10.1.1, шаги 2–4; п. 10.1.2, шаги 2–5), у облачных моделей лимит или неверный ключ. Состояние каждой модели — «Настройки → Помощник → Проверить связь»; причина — в журнале (`assistant.provider_failed provider=… reason=…`, без ключей).

- **«Вход не настроен» (503):** в `.env` не задан `APP_PASSWORD`/`APP_PASSWORD_HASH`, пароль короче 12 символов или остался `СМЕНИТЕ_МЕНЯ`; с профилями — неверный логин в `APP_USERS`, повтор логина или ни у одного профиля нет пароля. Причина — в журнале (`auth.not_configured reason=…`).
- **«Неверный логин или пароль», а пароль верный:** проверьте логин (латиница, как в `APP_USERS`); если пароль меняли в приложении, действует он, а не `.env` → п. 9.4.
- **Вход сразу возвращает на /login с сообщением «Запрос пришёл не с этого сайта»:** адрес в браузере не совпадает с `APP_URL` (проверьте порт `:8443`) и с хостом, который передаёт прокси.
- **unhealthy / `dataWritable:false`:** нет прав на `/volume1/docker/pora/data` → см. п. 1.3 (права или `PUID`/`PGID` в `.env`).
- **`Failed to load …/.env` / `env file … not found`:** нет файла `/volume1/docker/pora/.env` или он назван иначе (`.env.txt`) → п. 2.
- **Пароль «не подходит», а в журнале `The "…" variable is not set`:** в пароле есть `$` без кавычек → возьмите значение в одинарные кавычки или используйте `APP_PASSWORD_HASH` (п. 2), затем пересоздайте контейнер.
- **Container Manager → «Журнал»: «Журналы отсутствуют»:** в `compose.yaml` остался блок `logging:` (например, `driver: json-file`) → удалите его и пересоздайте контейнер (`sudo docker compose up -d --force-recreate`). Новый контейнер получит драйвер Synology `db`. Записи, сделанные при старом драйвере, во вкладке не появятся; их видно через `sudo docker logs pora-app`, пока контейнер не пересоздан.
- **Слишком много попыток (429):** подождите 15 минут или перезапустите контейнер.
- **Восстановить данные из копии:** п. 8.1 (`restore-backup.mjs`); очищать данные сайта на устройствах не нужно.
- **Устройство потеряно / пароль мог утечь:** смените пароль в `.env`, пересоздайте контейнер; или без смены пароля — «Выйти на всех устройствах» (п. 7).

## 12. Вложения (1.9.0)

Фото, PDF, сканы, документы и таблицы к задачам и проектам хранятся на NAS:

```
/volume1/docker/pora/data/attachments/
├── files/       ← сами файлы, имя = случайный id (без исходных имён и путей)
└── meta.json    ← до 1.12: кому принадлежит файл, к чему прикреплён, тип и размер
```

С 1.12.0 список вложений (владелец, задача/проект, тип, размер) хранится в базе `data/pora.db`, а сами файлы по-прежнему лежат в `attachments/files/` — их в базу не переносят. Поэтому `attachments/files/` нужно сохранять в Hyper Backup вместе с `backup/`.

- Папку контейнер создаёт сам при старте; отдельно ничего настраивать не нужно.
- Скачать файл может только вошедший профиль, который видит задачу или проект (для общих — все участники). Ссылки вида `/api/attachments/<id>` без входа не открываются.
- Принимаются JPEG, PNG, WebP, HEIC/HEIF, PDF, а также DOC, DOCX, XLS, XLSX, ODT, ODS, CSV, TXT, RTF. Тип проверяется по содержимому файла (DOCX/XLSX/ODT/ODS — по внутренней структуре, DOC/XLS — по заголовку, CSV/TXT — только текст в UTF-8). Файлы с макросами (DOCM, XLSM и такие же внутри DOCX/XLSX), архивы, программы, скрипты и HTML не принимаются. Документы отдаются только на скачивание (браузер их не исполняет); TXT и CSV видны прямо в приложении. Фото сжимаются на телефоне до 1920 px по длинной стороне. HEIC/HEIF с iPhone, если браузер не смог их превратить в JPEG сам, конвертируются на сервере (остаётся обычный JPEG с превью). Дата съёмки из EXIF показывается в приложении подписью под фото.
- Предел размера одного файла — переменная **`ATTACH_MAX_MB`** (по умолчанию `25`, максимум `200`). Если меняете — добавьте в `.env` строку `ATTACH_MAX_MB=50` и пересоздайте контейнер («Остановить» → «Собрать»). Если перед контейнером стоит Reverse Proxy DSM, его лимит тела запроса тоже должен быть не меньше (по умолчанию в DSM он достаточно большой).
- Без сети файл остаётся на телефоне и отправляется, когда появится связь. «Выйти» стирает с телефона и неотправленные файлы.
- **Автоочистка.** Раз в 6 часов (и через минуту после старта) сервер проверяет файлы: если файл не упомянут ни в одной задаче или проекте (задачу или проект удалили, вложение убрали), он помечается, а через **`ATTACH_ORPHAN_DAYS`** дней (по умолчанию `30`, как у корзины удалённого) стирается с NAS. Если задачу восстановили раньше — пометка снимается, файл остаётся. Файлы моложе суток не трогаются (могут ещё не дойти с телефона). Если в данных нет ни одной задачи и ни одного проекта (например, повреждён или подменён файл данных), очистка ничего не делает. Каждый проход пишется в журнал контейнера строкой `attach.cleanup` (сколько помечено, удалено, оставлено).

### Ссылки и контакты задачи (1.9.1)

- Ссылки и контакты задачи хранятся вместе с задачей (в `data/`), на NAS отдельно ничего не создаётся. `.env` менять не нужно.
- Подсказка названия ссылки: сервер сам открывает страницу (`GET /api/link-title`, только для вошедшего профиля, до 20 запросов в минуту). Он ходит только на публичные адреса http/https (порты 80, 443, 8080, 8443): локальные и частные сети (127.x, 10.x, 172.16–31.x, 192.168.x, 169.254.x, IPv6 `fc00::/7`, `fe80::/10` и т. п.) запрещены — и сразу, и после DNS, и после каждого перенаправления; подключение идёт ровно к проверенному адресу. Таймаут 5 с, читается не больше 256 КБ, только HTML. Если контейнер без выхода в интернет — подсказки просто не будет.
- Фото «до/после» из 1.9.0 не удаляются: это обычные вложения задачи, они видны в ленте.

## 13. Обслуживание (1.10.0)

- Карточки, правила, история, «Что болит» и статистика лежат там же, где задачи (с 1.12.0 — в базе `data/pora.db`, раньше — в `data/pora.json`). Они входят в встроенные копии `data/backups` и в Hyper Backup вместе с остальным (раздел 8). `.env` менять не нужно, переносить данные не нужно: в старых данных раздела просто нет, он создаётся пустым.
- Файлы (фото чеков, документы) — те же вложения, что у задач: `data/attachments`, `ATTACH_MAX_MB`, автоочистка `ATTACH_ORPHAN_DAYS`. Файл, на который ссылается карточка или её запись, очистка не трогает; файлы удалённой карточки стираются через `ATTACH_ORPHAN_DAYS` дней. Если в данных остались только карточки (нет ни задач, ни проектов), очистка по-прежнему работает.
- **Напоминания** — обычные задачи: по правилам и «Обновите пробег» приложение создаёт задачу с напоминанием, а пуш отправляет тот же планировщик, что и для остальных задач (раздел 11; ключи уведомлений те же). Задачи для правил **по дате** создаются заранее — за 45 дней до начала «скоро», когда приложение открыто; пуш за 14 дней (порог настраивается в карточке) придёт, даже если приложение закрыто. Для правил **по пробегу** задача появляется, когда вы обновили пробег и до срока осталось меньше порога («500 км»): сервер пробег не знает, поэтому без обновления пробега напоминания по км не будет — для этого есть ежемесячное «Обновите пробег».
- Общий доступ к карточке: тот же механизм владелец/участники, что у общих дат; участники видят и дополняют карточку, напоминания приходят владельцу.

### 13.1. Версия 1.10.1

Миграции и новых настроек нет. Новые поля (`todo`, `planDate`, `planKm`, `taskMade` у заметок «Что болит», `links` и `contacts` у карточек) лежат в том же документе и входят в резервные копии. Файлы записей и заметок хранятся рядом с остальными вложениями и очищаются вместе с ними.

### 13.2. Версия 1.11.0 (авто и техника)

- Миграции и новых настроек нет, `.env` менять не нужно. Новые поля лежат в той же карточке и в том же документе (`data/`), синхронизируются по полям и входят в резервные копии: у автомобиля — `fuel` (заправки), у правил — `cat: "ins"` (страховка/налог) и `cost` (обычная сумма), у записей истории — `cat`; у техники — `price`, `warrantyMonths` / `warrantyUntil`, `serial`, `warnDays`, `parts` (компоненты). Старые карточки открываются как раньше: этих полей у них просто нет.
- Чеки и гарантийные талоны компонентов — обычные вложения карточки (`data/attachments`, тот же лимит `ATTACH_MAX_MB` и автоочистка `ATTACH_ORPHAN_DAYS`). Удалили компонент — его файлы, ссылки и контакты удаляются вместе с ним.
- **Напоминание о конце гарантии** — обычная задача «Гарантия заканчивается: …» за 30 дней (в карточке можно поменять; 0 — выключить). Задача создаётся, когда приложение открыто, не раньше чем за 45 дней до дня напоминания; пуш приходит через тот же планировщик (раздел 11), даже если приложение закрыто. Изменили срок гарантии — старая задача убирается, появляется новая; удалённая вручную задача повторно не создаётся.

## 14. Хранилище SQLite (1.12.0)

- Файл `data/pora.db` (SQLite, режим WAL, внешние ключи, `synchronous=FULL`); каждая запись — одна транзакция. Версия схемы — таблица `schema_migrations`; база от более новой версии приложения не открывается (на старом образе — `storage.fatal`, данные не трогаются).
- Задачи, списки, привычки, вехи, проекты, карточки и их вложенные части (теги, чек-лист, даты повтора, участники, ссылки, контакты, отметки привычек, правила, история, заправки, комплектующие и т. д.) — отдельные таблицы. Каждая запись хранится вместе с отметками времени по полям, поэтому слияние на сервере идёт ровно как раньше.
- Переменные (необязательно): `DB_SNAPSHOT_HOUR` (0–23, по умолчанию 3) и `DB_SNAPSHOT_KEEP` (1–365, по умолчанию 7) — ночной снимок `backup/pora-<дата>.db`.
- Скрипты (`restore-backup.mjs`, `reset-password.mjs`, `export-json.mjs`, `db-snapshot.mjs`) можно запускать при работающем сервере: они пишут от имени владельца папки `data/` и не мешают синхронизации.
- Встроенные копии `backups/pora-*.json` продолжают делаться в прежнем формате — их можно открыть любым редактором и восстановить через `restore-backup.mjs`.

## 15. Быстрое добавление с iPhone (1.13.0)

Веб-приложение не может стоять в меню «Поделиться» iOS, поэтому используется команда «Быстрых команд» «В Пору», которая отправляет текст, ссылку или фото на сервер — во «Входящие» (у задачи пометка «📱 с iPhone»).

- **Ключ устройства** — «Настройки → Быстрое добавление → Новый ключ». Ключ показывается **один раз**; на сервере хранится только его хэш (sha256). Ключ умеет только добавлять во «Входящие» и ничего не читает. У каждого устройства свой ключ, «Отозвать» — сразу. Смена пароля и «Выйти на всех устройствах» отзывают все ключи профиля.
- **Адрес:** `POST https://<ваш адрес>/api/quick-add`, заголовок `Authorization: Bearer <ключ>`. Тело — JSON `{"text": "…", "url": "…"}` или форма (multipart) с полями `text`, `url`, `file`. Текст — до 4 КБ (первая строка — название, остальное — заметка). Ссылка — только http/https, сервер подставит заголовок страницы (адреса домашней сети не открываются). Файл — по правилам вложений (`ATTACH_MAX_MB`, тип по содержимому, HEIC → JPEG).
- **Ограничения:** 30 добавлений в минуту на ключ; неверные ключи тормозятся и блокируются по IP, как вход. В журнале — `quick_add.ok key=<id>` (только номер ключа, не сам ключ), `quick_add.bad_key`, `quick_add.rate_limited`.
- Нужна база SQLite (1.12+). Без сети на телефоне команда просто покажет ошибку — повторите позже.
